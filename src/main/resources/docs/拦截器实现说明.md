# Level 等级权限系统 - 拦截器实现说明

## 一、实现原理

### 核心思想
不再使用注解方式，而是通过 **Spring 拦截器** 在请求到达 Controller 之前，自动查询数据库中的 `interface_level` 表，动态判断用户是否有权访问该接口。

### 工作流程

```
用户请求
  ↓
LevelInterceptor（等级拦截器）
  ↓
1. 获取请求路径和方法
  ↓
2. 查询当前用户的 level
  ↓
3. 查询 interface_level 表中该接口需要的 level
  ↓
4. 比较：用户 level <= 接口要求 level？
  ↓
是 → 允许访问 → Controller
否 → 拒绝访问 → 返回错误
```

## 二、核心代码

### 1. LevelInterceptor（等级拦截器）

**文件位置：** [`LevelInterceptor.java`](file://d:\项目\test\src\main\java\com\project\test\common\interceptor\LevelInterceptor.java)

**核心逻辑：**
```java
@Override
public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
    // 1. 获取请求路径和方法
    String requestURI = request.getRequestURI();
    String method = request.getMethod();
    
    // 2. 获取当前用户 ID
    Long currentUserId = SecurityUtil.getCurrentUserId();
    
    // 3. 查询当前用户的等级
    LoginRequest currentUser = levelUserMapper.findById(currentUserId.intValue());
    Integer userLevel = currentUser.getLevel();
    
    // 4. 查询接口需要的等级
    InterfaceLevel interfaceLevel = findInterfaceLevel(requestURI, method);
    Integer requiredLevel = interfaceLevel.getRequiredLevel();
    
    // 5. 权限验证
    if (userLevel > requiredLevel) {
        throw new CommonException("等级不足");
    }
    
    return true; // 允许访问
}
```

### 2. WebConfig（拦截器配置）

**文件位置：** [`WebConfig.java`](file://d:\项目\test\src\main\java\com\project\test\common\config\WebConfig.java)

**配置代码：**
```java
@Override
public void addInterceptors(InterceptorRegistry registry) {
    // Level 等级拦截器
    registry.addInterceptor(levelInterceptor)
            .addPathPatterns("/**")
            .excludePathPatterns(
                "/auth/register",
                "/auth/login",
                "/**/register",
                "/**/login"
            );
}
```

## 三、使用方式

### 1. 配置接口等级

在 `interface_level` 表中配置接口需要的等级：

```sql
INSERT INTO interface_level (interface_path, interface_method, required_level, description) VALUES
('/api/level/interfaces', 'GET', 1, '查询所有接口等级配置'),
('/auth/level/modify', 'POST', 1, '修改用户等级'),
('/auth/password/modify', 'POST', 2, '修改用户密码'),
('/api/user/**', 'GET', 3, '用户查询接口'),
('/auth/login', 'POST', 999, '用户登录');
```

### 2. Controller 无需任何注解

**之前（注解方式）：**
```java
@RequireLevel(1)
@PostMapping("/level/modify")
public Result modifyLevel(...) {
    // ...
}
```

**现在（拦截器方式）：**
```java
// 不需要任何注解！
@PostMapping("/level/modify")
public Result modifyLevel(...) {
    // ...
}
```

### 3. 动态修改接口等级

**通过 API 修改：**
```bash
PUT /api/level/interface
Content-Type: application/json

{
  "id": 1,
  "requiredLevel": 2  // 将接口等级从 1 改为 2
}
```

**直接修改数据库：**
```sql
UPDATE interface_level 
SET required_level = 2 
WHERE id = 1;
```

修改后**立即生效**，无需重启服务！

## 四、权限验证规则

### 验证逻辑
```
用户等级 <= 接口要求等级 → 允许访问
用户等级 > 接口要求等级 → 拒绝访问
```

### 示例

| 接口 | 配置等级 | level 1 | level 2 | level 3 | level 999 |
|------|---------|---------|---------|---------|-----------|
| /api/level/interfaces | 1 | ✅ | ❌ | ❌ | ❌ |
| /auth/password/modify | 2 | ✅ | ✅ | ❌ | ❌ |
| /api/user/list | 3 | ✅ | ✅ | ✅ | ❌ |
| /auth/login | 999 | ✅ | ✅ | ✅ | ✅ |

## 五、路径匹配规则

### 1. 精确匹配
```
接口路径：/api/user/list
配置路径：/api/user/list
结果：✅ 匹配
```

### 2. 通配符匹配（**）
```
接口路径：/api/user/list/123
配置路径：/api/user/**
结果：✅ 匹配

接口路径：/api/user
配置路径：/api/user/**
结果：✅ 匹配（支持不带斜杠）
```

### 3. 简单通配符（*）
```
接口路径：/api/user/list
配置路径：/api/*/list
结果：✅ 匹配
```

### 匹配优先级
1. **精确匹配** 优先
2. 如果没有精确匹配，尝试 **通配符匹配**
3. 如果都没有匹配，**允许访问**（默认开放）

## 六、优势对比

### 注解方式 vs 拦截器方式

| 特性 | 注解方式 | 拦截器方式 |
|------|---------|-----------|
| **灵活性** | ❌ 低，需要修改代码 | ✅ 高，数据库配置即可 |
| **动态性** | ❌ 需要重启服务 | ✅ 实时生效 |
| **维护成本** | ❌ 高，每个接口都要加注解 | ✅ 低，统一处理 |
| **代码侵入** | ❌ 高，污染 Controller | ✅ 无，业务代码纯净 |
| **配置方式** | ❌ 代码硬编码 | ✅ 数据库动态配置 |
| **推荐度** | ❌ 不推荐 | ✅ 强烈推荐 |

## 七、完整示例

### 场景：新增一个用户删除接口

#### 步骤 1：编写 Controller（无需注解）
```java
@DeleteMapping("/user/{id}")
public Result deleteUser(@PathVariable Long id) {
    // 业务逻辑
    return Result.success("删除成功");
}
```

#### 步骤 2：配置接口等级
```sql
INSERT INTO interface_level (interface_path, interface_method, required_level, description) 
VALUES ('/api/user/{id}', 'DELETE', 2, '删除用户接口');
```

#### 步骤 3：测试
- level 1 用户访问 → ✅ 允许
- level 2 用户访问 → ✅ 允许
- level 3 用户访问 → ❌ 拒绝

#### 步骤 4：动态调整（可选）
如果觉得等级太高，可以动态调整：
```sql
UPDATE interface_level SET required_level = 1 WHERE id = 10;
```
**立即生效**，无需重启！

## 八、注意事项

### 1. 公开接口
以下接口不需要登录和等级验证：
- `/auth/login` - 登录
- `/auth/register` - 注册
- `OPTIONS` 请求 - CORS 预检

### 2. 默认开放策略
如果接口在 `interface_level` 表中**没有配置**，默认**允许访问**。

**建议：** 生产环境应该配置所有接口的等级。

### 3. 通配符使用
- 使用 `/**` 匹配所有子路径
- 使用 `*` 匹配单个路径段
- 精确路径优先级最高

### 4. 性能优化
- `interface_level` 表已建立索引
- 支持缓存（可选）
- 建议定期清理无用配置

## 十、总结

### 核心优势
✅ **完全动态** - 数据库配置，无需改代码  
✅ **实时生效** - 修改后立即生效，无需重启  
✅ **零侵入** - Controller 代码干净，无注解污染  
✅ **灵活配置** - 支持精确匹配和通配符  
✅ **统一管理** - 所有接口等级在一个表中  

### 使用建议
1. 所有接口都应该在 `interface_level` 表中配置
2. 新接口开发完成后，立即配置等级
3. 定期审查接口等级配置
4. 生产环境建议开启缓存
